⏺ Good morning. Here is the whole picture, in plain terms.

  The problem we're solving

  While an LLM generates an answer, it keeps a growing "memory" of everything so
  far (the KV cache). You can compress that cache to save GPU memory, but for
  some prompts compression visibly damages the answer, and you only find out
  after the damage is done. HERALD's controller decides, live, during
  generation, whether and when it is safe to switch to the compressed cache for
  each individual prompt.

  What the controller achieves

  The headline metric is: what fraction of the answer gets generated on the
  compressed cache, while keeping quality damage under a strict budget (at most
  0.03 quality drop on average). Measured live on 552 episodes (46 test prompts,
  4 compression strengths, 3 compression methods):

  ┌────────────────────┬───────────────┬────────────┬────────────┬─────────┐
  │                    │    Answer     │  Quality   │  Wasted    │         │
  │     Compressor     │  generated    │   cost     │  runtime   │ Extra   │
  │                    │  compressed   │  (budget   │  (target   │ tokens  │
  │                    │               │   0.03)    │    15%)    │         │
  ├────────────────────┼───────────────┼────────────┼────────────┼─────────┤
  │ expected_attention │ 79%           │ 0.003      │ 2.0%       │ 1.1%    │
  ├────────────────────┼───────────────┼────────────┼────────────┼─────────┤
  │ streaming_llm      │ 36%           │ 0.021      │ 5.1%       │ 3.0%    │
  ├────────────────────┼───────────────┼────────────┼────────────┼─────────┤
  │ knorm              │ 12%           │ 0.012      │ 8.4%       │ 4.5%    │
  └────────────────────┴───────────────┴────────────┴────────────┴─────────┘

  On "percentage of memory": the table's first column is the honest number we
  measure. Actual bytes saved are roughly that fraction times the compression
  strength (we test removing 25% to 87.5% of the cache). So for
  expected_attention at the strongest setting, about 80% of the generation runs
  on a cache that is 87.5% smaller. The three compressors differ because they
  differ in how often compression is safe at all: the theoretical ceilings (a
  controller with perfect foresight) are 96%, 89%, and 78%, so
  expected_attention is close to perfect, while knorm compression is simply
  rarely safe, and the controller correctly refuses it most of the time.
  Refusing costs nothing: quality stays intact.

  How it works

  1. Generate normally, watch for openings. The answer decodes on the
  uncompressed cache. Every 16 tokens is a potential switch point.
  2. Free pre-check (the gate, built yesterday). At each switch point, a tiny
  CPU model looks at statistics of the tokens generated so far (entropy,
  confidence trends, etc., maintained incrementally for 0.1 ms) and predicts
  whether a compression attempt is likely to succeed here. If not, skip it. This
  deleted 40-66% of the expensive probes and is what pushed the wasted runtime
  under the target.
  3. Cheap probe (the alarm). If the gate says try: build the compressed cache,
  generate just 2 tokens on it, and a frozen model scores those 2 tokens'
  statistics. Commit if safe, otherwise throw the 2 tokens away and continue
  uncompressed. A failed probe costs only those 2 tokens.
  4. Commit is free. If the alarm says safe, the same generation call simply

  2. How the compression actually works right now

  The current controller makes a one-shot, irreversible switch. The whole answer
  starts generating on the full uncompressed cache. At each switch point we ask
  "is it safe to compress NOW?". The moment we commit, the cache built so far

  generates on that compressed cache. We never un-compress and never change the
  strength. Also, the strength (25%, 50%, 75%, 87.5% removed) is currently an
  input we evaluate separately, not something the controller chooses: it only
  picks when, not how much.

  Your idea, predicting the compression level as a regression and letting it
  move up and down during generation, is exactly the planned next research phase
  (it's the TCP/AIMD item in our roadmap: ramp compression up while the signals
  say safe, back off when the alarm fires). Two honest caveats on it: first,
  "decompressing" is not free, since evicted cache entries are gone; going back
  means re-computing them, so the realistic version is "choose how much more to
  compress at each step", a ratchet with careful increments, not a free dial.
  Second, this is the first idea our replay cannot test: the recorded data only
  contains one-shot switches, so an adaptive-ratio controller needs new GPU
  trajectories. That's precisely what the Phase B campaign would record, and why

  3. How it works now, in five lines

  1. Generate the answer normally (uncompressed), pausing at every 16th token.
  2. At each pause, a free CPU check (the gate) estimates whether compression
  could stick here. Usually it says no, and we just keep generating.
  3. If it says maybe: build the compressed cache, generate 2 trial tokens on
  it, and a frozen model (the alarm) scores their statistics.
  4. Alarm says safe: keep the compressed cache and finish the answer on it.
  Alarm says unsafe: discard the 2 tokens, continue uncompressed, try again at a
  later pause.
  5. If no point is ever safe, the answer completes uncompressed and quality is
  untouched.

  4. How quality cost is measured, and my assessment

  Each test prompt comes from IFEval, a benchmark of verifiable instructions
  ("answer in exactly 3 bullet points, no capital letters"). Quality q is the
  fraction of instructions the finished answer actually satisfies, checked
  programmatically. Cost is paired: q(uncompressed reference) minus
  q(controller's output) for the same prompt, averaged over all episodes, with
  the budget requiring that average stay at or below 0.03.

  - Limit 1, the mean hides tails. An average of 0.02 could be many harmless
